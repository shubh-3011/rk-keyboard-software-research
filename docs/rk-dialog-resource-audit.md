# RK Windows dialog-resource audit

## Scope and method

This audit statically parses Win32 `RT_DIALOG` resources embedded in the
installed RK 4.06 package. It reads PE resource bytes from the five named
executables/DLLs in the audit script; it does not launch them. The output
includes the resource ID, language ID, template format, title/font/style,
and each declared control's ID, class, caption, and rectangle. The complete
machine-readable inventory is
[`rk-dialog-resource-controls.csv`](rk-dialog-resource-controls.csv),
generated by [`audit_dialog_resources.py`](../scripts/audit_dialog_resources.py).

The parse produced **52 rows**: 43 control rows and nine templates with no
controls. It had no parse errors. Resources with no controls are evidence of
empty templates in the PE, not proof that the associated runtime window is
empty; MFC can create and skin controls dynamically. Resource IDs and labels
also do not establish when a dialog appears or what every control does.

To regenerate the inventory, install the pinned audit dependency and pass the
installed package directory:

```powershell
python -m pip install -r requirements-audit.txt
python scripts/audit_dialog_resources.py `
  --rk-root "C:\Program Files (x86)\RK Keyboard Software" `
  --output docs/rk-dialog-resource-controls.csv
```

## Main application resources

`DeviceDriver.exe` contains ten dialog templates across the parsed language
resources. Seven controls occur in two templates: a generic `New` dialog
(five standard controls) and a generic `Dialog` template (OK/Cancel). The
other eight templates declare zero static controls. This is consistent with
the earlier evidence that the visible RK feature UI is largely MFC/runtime
generated; resource inventory alone cannot reconstruct all visible feature
pages or bind every XML text key to a widget.

The locale loader has a separate code-backed path: the main UI XML format
string `%sText\\%s\\text.xml` is referenced at VA `0x00445C5C`, and startup
calls the loader at `0x00441F20` from `0x00445CA8`. LED labels use a
profile-specific path `%sDev\\%04X\\%s\\led.xml` at `0x00422B84`, followed
by a generic locale path `%sDev\\%s\\led.xml` at `0x00422BDB`. Nearby code
constructs keys `tc_eft%d`, `tc_led_mode%d`, and `tc_led%d`. The branch order
supports profile-specific-first, generic-fallback behavior. The loader's
exact COM/XML success semantics, each key's widget binding, and the associated
LED command mapping remain unresolved. See the
[resource/localization audit](rk-resource-localization-audit.md).

## Bundled updater dialog

`Dev/01AF/Update.exe` resource 102, language ID 1028, is the
“8805PH Update Tool-V1.22” dialog and declares 25 controls. Its labels include
one-click upgrade, BLE version read, firmware/device information buttons,
VID/PID fields, a file chooser, a “specify” checkbox, and a dongle pairing
preservation checkbox. A neighboring About dialog (resource 100) contains
four controls, including the 1.22 tool version and Sinowealth copyright text.
Language ID 1028 is recorded as stored; captions are retained literally in
the CSV.

Selected control-to-handler links were separately established from the
updater's MFC `WM_COMMAND` map and static disassembly:

| Resource 102 control ID | Stored caption | Handler | Static interpretation and limit |
| --- | --- | --- | --- |
| `0x0419` | 一键升级 (one-click upgrade) | `0x00409DC0` | Upgrade-click handler. Its exact complete state sequence remains under audit. |
| `0x03E9` | 选择... (browse/select) | `0x0040B0A0` | File-selection handler. |
| `0x041D` | 读BLE版本 (read BLE version) | `0x0040C2C0` | Sets dialog flag `this+0x8E6C=1` and enters a shared BLE/version workflow at `0x0040A0F0`. |
| `0x0422` | Dongle保留对码信息 | `0x0040C2D0` | Reads a checkbox with `BM_GETCHECK` and stores it in global `0x005C5F09`; its exact effect on later transfer bytes is not yet recovered. |
| `0x0423` | 指定 (specify) | `0x0040C6D0` | Toggles VID/PID edit fields `0x0424`/`0x0425` according to checkbox state. |

Controls `0x0428` (“firmware information”) and `0x042A` (“device information”)
do not have a matching handler in the scanned `WM_COMMAND` entries. They may
be handled through another message/virtual path or have no active action; this
is unresolved. This selected crosswalk is not a complete map of updater
message types or runtime behavior. The updater audit is in
[`rk-firmware-readback-audit.md`](rk-firmware-readback-audit.md).

## Limits

This inventory is specific to the installed RK package version 4.06 and its
single bundled updater. It does not cover every RK software release or every
keyboard model. It does not infer control behavior from captions, execute
firmware operations, or establish what appears on screen at runtime. The full
MFC/action map, dynamic UI contents, and all updater message/callback targets
remain open work.
