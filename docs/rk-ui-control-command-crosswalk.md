# RK UI control-to-command crosswalk

## Scope and method

This report cross-references visible labels and static dialog controls with the recovered MFC message maps and statically identified device-action paths in the installed RK Keyboard Software 4.06 snapshot. The main executable is `DeviceDriver.exe`, SHA-256 `C03F88BC4E2D78AA4392D7445B0FD62182DC824F97F5D5DB40BD009E547A9AB6`. The bundled updater is `Dev/01AF/Update.exe` and its resource 102 dialog is language ID 1028. Addresses are image virtual addresses for these particular binaries.

The evidence used here is the parsed dialog inventory, English localization XML and locale inventories, recovered MFC message-map rows and owner evidence, the existing Ghidra exports, and the linked static audits. The software and updater were not launched. A separate live descriptor check opened read-access handles for the present `258A:0150` HID collections and parsed preparsed capabilities only; this crosswalk pass read no input report and sent no output or feature report or device command.

Evidence labels used below:

- **Proven statically** means the resource, localized key use, message-map row, or native control/data-flow edge is directly present in the audited snapshot.
- **Inferred** means the available code and strings suggest a relationship but do not establish the concrete control, runtime branch, or device object.
- **Unresolved** means no reliable edge was recovered. A caption or a feature serializer alone is not a control-to-command mapping.

## Summary

The main `DeviceDriver.exe` has very few ordinary static dialog controls. Its feature UI is mostly constructed dynamically. The string resources expose labels for macro, lighting, screen, brightness, and key-mapping workflows, but the installed XML does not contain control IDs. The MFC inventory now recovers five application-owned maps (`CLedDlg`, `CMacroDlg`, `CScreenDlg`, `COemDrvApp`, and `COemDrvDlg`), with six `WM_COMMAND` entries and 14 additional `CLedDlg` window-message entries. Consequently, most feature labels cannot be assigned a unique child HWND/control ID and handler from the present static evidence.

The bundled updater is a stronger control crosswalk: its resource 102 has 25 declared controls, and five click/checkbox controls have direct resource-ID-to-handler matches. Some actions then reach a device/updater workflow, but this does not make the updater safe to run or establish every transfer effect.

### Main executable resource coverage

The parsed main executable dialog resources contain 10 templates; only two templates declare controls (the generic `New` dialog and generic `Dialog` with OK/Cancel), and eight templates declare none. In particular, the localized feature labels are not accompanied by a resource dialog containing their corresponding control IDs. The parsed count is 52 rows total: 43 control rows and nine no-control templates across the audit set, which also includes the updater and uninstaller. Consult [`rk-dialog-resource-controls.csv`](rk-dialog-resource-controls.csv) for exact resource/language/control rows.

The MFC audit recovers 27 unique arrays with 305 non-sentinel entries. Five app-owned arrays are identified: `CLedDlg` (14 entries), `CMacroDlg` (13), `CScreenDlg` (7), `COemDrvApp` (1), and `COemDrvDlg` (15). Together these have six `WM_COMMAND` entries; the `CLedDlg` map contributes 14 other window messages. The remaining recovered arrays primarily belong to MFC framework classes; they should not be described as RK feature handlers. The full raw map is [`rk-mfc-message-map-entries.csv`](rk-mfc-message-map-entries.csv), with owner attribution in [`rk-mfc-map-owner-evidence.csv`](rk-mfc-map-owner-evidence.csv).

## Findings that cannot be made reliably from this snapshot

- There is no complete static ID/label/handler table for the main feature UI. XML leaf keys are strings; they do not encode control IDs. Runtime-generated controls and code-built layouts must be traced individually.
- No robust visible control-to-command link was recovered for the generic LED/effect selectors, per-key lighting editor, brightness increment/decrement/loop actions, most key-remap actions, macro import/export/recording buttons, screen image import/save/transfer buttons, profile switching, or reset/factory-restore prompts.
- A matching serializer branch does not prove a given visible control invokes it. Several apply workers dispatch through virtual methods, and the active receiver/profile is not statically observed.
- Resource captions can be misleading without styles: the updater “firmware information” and “device information” entries are group boxes, not buttons.
- The language label `tc_adv_str13`, generated-control label `tc_apply`, and generic LED dictionary keys are not enough to recover the control ID. `tc_apply` also occurs on two distinct controls with different handlers and behavior.
- The package and addresses cover one installed 4.06 snapshot and its bundled updater. The profile catalog contains 189 `KB.ini` entries and family mappings, but this crosswalk does not prove that all RK product revisions, firmware variants, or later software releases use the same controls, routes, or protocols.

For the installed profile-to-driver-family classification, see [`rk-profile-driver-family-map.csv`](rk-profile-driver-family-map.csv). It is a static profile selection map, not evidence that any specific device was connected during this analysis.
