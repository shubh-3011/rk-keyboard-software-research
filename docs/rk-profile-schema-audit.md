# RK profile catalog and `KB.ini` schema audit

This audit covers the RK Keyboard Software 4.06 files installed at
`C:\Program Files (x86)\RK Keyboard Software`. It reads `Cfg.ini`, each
`Dev/*/KB.ini`, the existing `models.json`, and the profile-handler CSV. It
does not launch RK software, open a keyboard interface, or send any device
command.

## Corpus and catalog coverage

`Cfg.ini` contains 188 `DevName` rows and 188 PID-list entries. The two sets
match, and each named code has a `KB.ini`. The installed `Dev` directory has
189 `KB.ini` files: the 188 named profiles plus `01C7`, which has no `DevName`
entry or configured PID. `01C7` is data found in the installation, not a
verified model identity; the handler map correctly has no row for it.

The configured default VID is `0x258A`. No profile `OPT` section contains a
`VID` or `DevTy` key. The named-profile VID shown in the map therefore comes
from the global configuration default, not an override stored in each
profile.

The profile families and region names in `models.json` are generated by
name-based heuristics. They are useful catalog labels, but are not explicit
vendor fields and have not been validated against physical units.

## `OPT` fields and value forms

Across all 189 files there are 88 distinct non-comment `OPT` fields and 6,506
assignments. No profile has a duplicate `OPT` key. The exhaustive field ledger
lists, for every field, its exact profile coverage and omissions, raw-value
vocabulary with frequencies, comma-list arities and token forms, inline
comments, and whether an individual field-name literal was found in
`DeviceDriver.exe`:

- [Per-field schema, values, and omissions](rk-profile-schema-fields.csv)
- [Read-only schema audit generator](../scripts/audit_profile_schema.py)

The type labels are lexical descriptions of the installed text: decimal
integer, `0x`-prefixed integer, text, or comma-separated values and their token
forms. They do not define signedness, units, enum meaning, or hardware payload
semantics. In particular, unprefixed numeric tokens in comma lists are
preserved as written; their interpretation is not inferred from their
appearance.

Some fields whose names suggest controls have limited or highly optional
coverage. For example, `Fw` is present in 65 files (raw values `0`, `1`, `2`),
`Psd` in 63, `LayerNum` in 33, `ShowScreen` in 15, `MacroBufferNum` in four,
and `ShowAutoDetect` in 46. The CSV contains exact values and the full list of
profile codes for all 88 keys, so these examples should not be mistaken for
the complete inventory.

All 189 files have `RGBKb`, with raw values `0` or `1`; 156 named models have
`RGBKb=1`. Fifteen profiles contain screen fields. Their `ShowScreen` values
are `1` or `2`, `RGBScreen` is `1` for all 15, and the stored dimensions are
320×172, 240×240, 240×135, or 128×128. These are profile declarations, not a
runtime capability probe.

There are 3,765 `LedOpt*` assignments, each a six-value comma-list. Slot
presence is irregular: 93 profiles contain slots 1–21; 53 contain 1–17 and
19–20; 28 contain 1–20; ten contain 1–19; four contain 1–13; and `01C7`
contains slots 1–3. This describes stored keys, not the effect of each tuple.
The source has 110 inline LED-option comments across `LedOpt1`, `LedOpt2`,
`LedOpt3`, `LedOpt4`, `LedOpt8`, `LedOpt9`, `LedOpt10`, `LedOpt14`, `LedOpt15`,
`LedOpt17`, and `LedOpt18`. Their text is retained separately in the field
ledger; it is not proof that a label selects a particular device command.

## Mapping sections and preservation limits

Every file has a `[KEY]` section. The 15,945 assignments use `K1`-style keys,
with row widths of eight values (15,731 rows), nine values (174), or ten
values (40). The numeric key IDs have no gaps within each profile's recorded
minimum-to-maximum range. The extractor uses the first four values as layout
rectangle coordinates; the remaining values are retained as mapping tuples,
but their columns are not fully decoded.

There are 63 `[FN1]` sections with 2,278 rows. Their row widths are three
values for 2,274 rows and four values for four rows. There are 17 `[FN2]`
sections with 603 rows, all three values wide. The exact section coverage,
record-ID ranges, arities, and lexical cell types are listed for every profile
in [the section-shape ledger](rk-profile-section-shapes.csv). Decoded
`[KEY]`, `[FN1]`, and `[FN2]` tuple values are stored in `models.json`.

The source's `[KEY]` comment labels are separate from the tuples. There are
preceding comment lines for 15,933 of the 15,945 `[KEY]` assignments; 12
assignments have none. The renderer in the catalog only exposes drawable
rectangles, so comments belonging to non-drawable or extra mapping rows are
not all represented in the visual-layout projection. The complete
profile/key/comment association is in
[the key-record ledger](rk-profile-key-records.csv).

The [profile tuple semantics report](rk-profile-tuple-semantics.md) separates
confirmed layout-coordinate extraction from candidate interpretations of
remaining `[KEY]`, `[FN1]`, `[FN2]`, and `LedOpt*` cells. Raw values remain
preserved because the translation from profile cells to device-specific
runtime records is not fully recovered.

`models.json` was compared against all 189 installed files: all `OPT` strings
matched exactly after the source parser's trimming and inline-comment rule;
all decoded base and Fn assignment maps matched with zero mismatches. The
comparison is on decoded tuple values. It does not preserve source whitespace
or the original numeric radix for tuple cells converted to JSON integers.

Two count comparisons remain unresolved rather than being treated as
corruption. Among the 188 named profiles, `LayoutKeyNum` differs from the
number of drawable rectangles in 134. It also differs from the number of raw
`[KEY]` assignments in 133 named profiles. For `022F`, for example,
`LayoutKeyNum=104`, there are 104 `[KEY]` assignments, and the drawable layout
has 102 rectangles. The other profiles show that these three counts are not
interchangeable; the catalog preserves each separately.

`LayerNum` also does not reliably enumerate the populated Fn sections. Of 33
profiles with `LayerNum`, 26 say `4` but contain only `[FN1]`, and seven say
`3` but also contain only `[FN1]`. Seventeen profiles have both `[FN1]` and
`[FN2]` but omit `LayerNum`; 13 have `[FN1]` only and omit it. As a result,
the `features.layers` convenience list in `models.json` is derived metadata,
not evidence that the named layers have stored mappings. This is especially
visible for S98 profile `022F`: `LayerNum=4`, 38 `[FN1]` rows, and no `[FN2]`
rows.

## Unregistered profile `01C7`

`01C7` has 25 `OPT` assignments and 104 `[KEY]` rows, but no `[FN1]` or
`[FN2]`. Its stored values include `Fw=0`, `RGBKb=0`, `LayoutKeyNum=104`, and
`MacroBufferNum=4`; it has `LedOpt1`–`LedOpt13`, but no `Psd` or screen
declaration. The installation also contains 13 English and 13 Simplified
Chinese profile-local LED labels. None of these facts supplies a model name,
configured USB identity, or confirmed native handler, so the profile remains
unregistered and unclassified at the model/handler level.

## S98 profiles

The installed config names eight S98 variants: `0174`, `01AF`, `01BF`, `0223`,
`0224`, `022B`, `022F`, and `0230`. All eight have raw `Fw=1`, `RGBKb=1`,
`ShowScreen=1`, `RGBScreen=1`, 320×172 screen dimensions, and a 60-frame
limit. All store LED slots 1–17 and 19–20, with no slot 18 or 21. Their raw
`Psd` strings are distinct. All eight omit wireless VID/PID fields. They also
store `DefBri=5`, `LightUI=0,4,8,12,16,20`, and
`LightHW=0,4,8,12,16,20`. The native profile initializer treats `DefBri` as
an index into the runtime lighting values, then the serializer maps that
index through `LightHW`; for these profile defaults the selected table value
is `20`. The physical brightness scale and user-control event mapping remain
unresolved. See the
[brightness profile/UI/serializer trace](reverse-engineering.md#brightness-profile-ui-and-serializer-path).

The [S98 variant ledger](rk-s98-profile-variants.csv) gives each profile's
raw `Psd`, mapping counts, screen fields, handler-map entry, and every raw
`OPT` difference from `022F`. `01AF` additionally stores `KbImgUse=0x0174`,
`NoUpdate=1`, and `VerNeedToUpdate=0x2108`. `0174` omits `LayerNum`; the other
seven use `LayerNum=4`. None has an `[FN2]` section. These profiles route to
`CDevG5KB` in the static direct-profile selector, based on their nonzero
`Fw`; confidence is high for that initial code path because the selector
branch was recovered statically. It is not a physical-device validation.

## Handler-map confidence and open points

All 188 configured named rows are direct PID profiles. The static selector
routes the 125 named rows with `Fw=0` (including omitted values that take the
loader's zero default) to `CDevRKKB`, and the 63 nonzero-`Fw` rows to
`CDevG5KB`. Confidence is high for this initial `Fw`-based branch in the
analyzed binary. The source does not prove a connected keyboard's firmware
revision or whether its HID descriptor will satisfy the remaining match
criteria.

The analysis recovered a conditional wireless/companion path that can
construct `CDev3632` after descriptor and six-byte comparison checks on a
nonzero-`Fw` row. A focused static trace establishes the profile signature
source: `FUN_00447210` calls `FUN_00447110`, which reads `[OPT] Psd`, parses up
to six hexadecimal bytes through `FUN_0044DC70`, and stores them at row
offsets `+0x04..+0x09`. `FUN_00415D20` obtains a six-byte result through
`FUN_0040E210` and passes it to `FUN_00415900`, which compares it against
eligible profile rows. This closes the static source-to-comparison path, but
not the semantic meaning of `Psd`, the full transition sequence, actual
runtime profile selection, or an exclusive one-handler-per-model mapping.
The direct feature reads recorded elsewhere used report IDs `05` and `0A`;
they are not evidence of a response to this specific helper call. The path
was not validated against a connected keyboard, and unclassified tuple
columns remain unresolved. See the [native reverse-engineering report](reverse-engineering.md).
