## Why this takes time

The source code, symbols, and a complete authoritative package catalog are unavailable. A binary can be disassembled, but recovering the original source-level behavior requires resolving indirect calls, virtual dispatch, callbacks, dynamic loading, resource/config dependencies, and model/revision gates. Similar filenames do not imply the same executable or protocol. Static callsites and import tables alone do not prove runtime behavior or device acceptance. The current hardware boundary is static and non-invasive: do not open the keyboard HID interface, intercept live communication, send reports or commands, run an RK updater, enter a bootloader, or write firmware.

The fastest reliable route is to group packages by binary hashes/code identity, automate manifests and repetitive inventories, then close one concrete UI → state/config → serializer → transport path per binary family. That yields verifiable chunks faster than treating “all RK software” as one file, while preserving unknowns explicitly. It still cannot produce a truthful completion date or a single percent without a finite package denominator.
